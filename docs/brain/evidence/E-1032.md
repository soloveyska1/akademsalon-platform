## Incident and recovery

The operator bot reported three `sqlite3.OperationalError: database is locked`
tracebacks at 03:50 MSK and seven at 04:22. By the bounded diagnostic at about
04:45, the journal contained 170 matching failures. The first captured stack
was the promo-eligibility session `last_used_at` write; `/api/orders` and the
minute scheduler's pending-handoff retry then failed through the same shared
database helper. systemd still reported the process active with `NRestarts=0`,
so service state alone did not express the incident.

SQLite integrity was not damaged. `PRAGMA quick_check` was `ok`, journal mode
was WAL and only the bot process had the database open. A graceful restart at
04:51:15 MSK replaced PID `513969` with PID `526605`, restored the listener and
cleared the poisoned connection. From that restart through the final release
preflight, the bounded journal scan found zero new lock tracebacks, scheduler
failures or request tracebacks. This was incident recovery, not the durable
fix.

## Root cause and deterministic proof

The shared `aiosqlite` connection served reads and ordinary writes, while
Analytics v2 correctly used short-lived independent writer connections. An
open read snapshot on the shared connection followed by an Analytics commit
made the next shared write an invalid WAL snapshot upgrade. SQLite returned
extended code 517, `SQLITE_BUSY_SNAPSHOT`, immediately despite the 5-second
busy timeout. The failed implicit transaction then left every unrelated helper
using the same process-wide connection unable to write until restart.

The focused test creates that exact two-writer sequence. The old lane raises
`database is locked`/`SQLITE_BUSY_SNAPSHOT`; the candidate's write-only
autocommit lane succeeds without retrying a statement or rolling back another
task. Analytics connections commit, roll back and close correctly; changing
Analytics was therefore neither required nor included.

## Installed design

The ordinary connection becomes `PRAGMA query_only=ON` after startup migrations
and remains the shared read lane. A second persistent connection uses
`isolation_level=None`; one `asyncio.Lock` serializes ordinary `_exec`
statements. Because the writer never serves reads and each statement is already
committed when `execute` returns, it cannot hold the stale snapshot or expose an
execute/commit await gap. There is deliberately no automatic replay and no
cross-task rollback.

Every direct runtime DML call in the exact ten live modules was migrated to the
writer or to an explicit `BEGIN IMMEDIATE` transaction. An AST gate rejects a
remaining literal write, an unreviewed dynamic SQL call and connection aliases
that execute non-read SQL. The query-only reader is a second fail-closed guard.
Known multi-write units preserve atomicity for QA, admin ban/session revoke,
deposit, handoff delivery and review paths.

Independent review exposed a pre-existing deposit concurrency weakness during
this migration. Activation now re-reads the pending row under `BEGIN
IMMEDIATE`, performs `pending -> active` compare-and-swap, and writes the top-up
plus bonus in that same unit-of-work. Refund similarly re-reads, performs
`active -> refunded` compare-and-swap, and atomically records money and bonus
effects. Two-task regressions prove exactly one activation/refund; an injected
bonus failure rolls the whole activation back.

The installer accepts only the exact coherent before or after inventory,
compiles candidates before publication, preserves uid/gid/mode, replaces each
source atomically and records a root-only manifest. Apply and rollback both add
a replaced source to their compensation set before post-replace verification;
injected failures prove they return to a coherent source set. The installer
never migrates, copies or restores SQLite data.
