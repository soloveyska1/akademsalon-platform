# E-1018 — 404 scanner noise не будит владельца

- Date: 2026-08-21, Europe/Moscow.
- source_type: privacy-safe live diagnosis + failing-first monitoring contract +
  bounded production watcher hotfix + executed rollback/forward drill.
- Canonical base: `4f3f13a07a1d3131979904296af75db0b72464ba`.
- Implementation: `088a8aa7204914194a72894a45b62a423fffb02a`.
- Workstream: `WS-34b0bf142575410db08618c733ed73c4`.
- Outcome: `OUT-006`; release gate: `G10`.

## Что произошло

Выделенный лог Akademsalon подтвердил ровно 500 ответов `404` между
`04:32:56` и `04:33:08 MSK`: все запросы были `GET`, а `5xx` за
интервал и за сутки равнялись нулю. Сайт, API, бот, база и диск одновременно
имели status `up`. Из-за внутреннего `error_page 404 /404.html`
privacy-safe лог намеренно не раскрывает исходные probes, но скорость 500
запросов за 12 секунд не является пользовательским переходом по одной
сломавшейся ссылке.

Источник legacy-вкладки «Визиты» содержал 0 строк за последние три часа; его
последняя строка датирована 10 августа. Новые consent-only таблицы Analytics v2
также были пусты. Это полезное подтверждение отсутствия совпадающей сессии, но
не доказательство само по себе: consent-only аналитика не является переписью
всех HTTP-запросов. Поэтому прежняя рекомендация alert-а вручную смотреть
«Визиты» не могла быть надёжным health gate.

Причиной повторного шума был сам контракт watcher: любое число свежих `404`
не меньше 40 создавало Telegram alert, суточный счётчик и часовой throttle.
Публичный интернет-скан неизбежно пересекал этот порог на исправном статическом
сайте.

## Исправленный контракт

- Сырые публичные `404` больше не создают alert, throttle или строку в
  утренней health-сводке. Старые ключи `day.404` и `throttle.404`
  удаляются при обычном цикле для совместимости с прежним state.
- Проверка `5xx` сохранена отдельно и без изменения порога: три свежих
  non-maintenance ответа создают прежний server-error alert; штатный `503`
  техработ по-прежнему исключён.
- Внутренние ссылки, sitemap, маршруты и обязательные статические ресурсы
  остаются под детерминированными repository-тестами и GET-only production
  smoke. Consent-only «Визиты» остаются продуктовой аналитикой, а не pager-ом.
- Точное изменение server-owned watcher хранится в
  `ops/monitoring/salon-watch-404-policy.patch`. Применение к проверенному
  base даёт байт-в-байт активный production hash.

Backend, SQLite, Nginx и static release не менялись и не перезапускались.
Production submit и другие пользовательские мутации не выполнялись. В
диагностике не выводились client IP, user-agent, referrer, query string,
контакты, заказы или тексты работ.

- Tracked patch, применённый к exact before source, скомпилировался и дал exact
  production hash `31f1f9…d06f`.
- Изолированный тест: 500 `404` → 0 alerts, без daily key/throttle; три
  `502` → 1 alert; десять maintenance `503` → 0 alerts.
- Live threshold test создал 50 реальных ответов `404` сверх прежнего порога,
  watcher полностью прочитал log delta, но не создал 404 key/throttle;
  `day.5xx` остался `0`.
- External и VPS matrices: `/`, API health, robots, sitemap и manifest равны
  `200`; случайный путь и PHP/WordPress probes равны `404`; canonical,
  www и legacy redirects равны ожидаемым `301`.
- Nginx, `salon-bot-v2.service`, fail2ban и `salon-watch.timer` активны;
  `nginx -t` чист. Все watcher checks имеют `up`.

  `c6e834…b130` для Kiskispace. `current` и `dist` по-прежнему указывают
  на `release158-fa2b317`; backend непрерывно работает с 12 августа.

Инцидент закрыт: сканеры продолжают получать честные `404`, но этот обычный
интернет-шум больше не маскируется под проблему посетителей и не будит
владельца. Настоящие `5xx` остаются немедленным сигналом.
