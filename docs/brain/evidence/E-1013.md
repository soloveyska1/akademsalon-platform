## User-visible incident and exact cause

The user reproduced that every otherwise-valid site request ended with:

> Сервер не подтвердил безопасный повтор. Номер попытки сохранён…

Read-only comparison proved a production-wide contract mismatch:

- the live configurator and guide producer sent
  `consent-request 1.0 · privacy 3.1 · oferta 3.2`;
- the published documents themselves are privacy 3.1, oferta 3.2 and request
  consent 1.0;
- the active backend still loaded privacy 3.0 and oferta 3.0; its exact
  `config.py` SHA-256 before repair was
  `2ae17e848cbcde333f8d44f6e87c372c36b70f768b2c379bce3547d2d47bbee9`;
- `/api/orders` returned `consent_version_mismatch` as HTTP 409 before request-ID
  lookup or database creation. The frontend rendered every 409 as an ambiguous
  safe-repeat conflict, which hid the real rejection;
- the same stale editions were present in `GIFT_CONSENT_DOC`, so gift checkout
  had the same defect.

This establishes that the reported failed attempt created no order: the consent
check precedes the first request-ID/database branch in the active backend.

## Authorized recovery

The write-owner preserved the exact previous file as
`/root/salon_bot/app/config.py.pre-consent-hotfix-20260803`, asserted its source
hash, generated and compiled a temporary replacement, then atomically installed:

- `DOC_EDITIONS["privacy"] = "3.1"`;
- `DOC_EDITIONS["oferta"] = "3.2"`;
- `GIFT_CONSENT_DOC = "consent-request 1.0 · privacy 3.1 · oferta 3.2 · gift form 2.0"`.

The new exact `config.py` SHA-256 is
`d15fd1f59dd4d4f8e756b79e26a4abf5116068cc66d66fad35c63ddd43fb93a9`.
The service was restarted once. An immediate first health request hit the normal
restart window and returned 502; the first bounded follow-up poll returned active
+ HTTP 200, so rollback was not needed.

## Post-recovery proof

The production VPS GET/HEAD-only smoke passed 14/14:

- seven public API dictionaries returned 200;
- `/me`, `/bonus`, `/deposit` returned 401 and both admin routes returned 403;
- the event route returned 200 with `ok:true`;
- the live configurator consent string exactly matched the active backend
  editions.

The service remained active; live configurator, privacy and oferta pages returned
200 and exposed the expected 1.0/3.1/3.2 editions. No real submit was used as a
test because the safe marker, isolated sink and complete cleanup proof remain
absent.

Local deterministic proof passed 52/52 focused submit/privacy tests, 39/39 Brain
tests and strict Brain validation with 65 records. Fresh conflict snapshot
`a067fcf2c7e8e552adada8a8f4f6c3040d65a00f9600f75f10dc7b2d83717662`
had hard=0, warnings=3 and info=5. The integration owner explicitly accepted
only terminal-worktree and dormant unmanaged-ref warnings; active dirty work was
disjoint from this declared scope.

## Rollback and follow-up

Rollback is exact: restore the preserved pre-hotfix file and restart
`salon-bot-v2.service`. That rollback is operationally available but would
reopen the confirmed outage, so it is only for a new health regression.

Two non-blocking tracked follow-ups remain:

1. `consent-request.html` still describes the linked privacy document as 3.0 in
   one sentence even though the linked document is 3.1; correct it in a normal
   frontend release.
2. Classify `consent_version_mismatch` as a definitive stale-page rejection with
   plain refresh guidance instead of presenting the generic ambiguous-retry copy.

The incident restores submission compatibility. It does not prove downstream
bot/operator delivery, durable outbox semantics or exact cleanup, and therefore
does not close the full `OUT-001` end-to-end outcome.
