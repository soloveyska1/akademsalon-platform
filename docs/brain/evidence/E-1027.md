## Incident and root cause

The production admin page still rendered its normal Telegram entry, and an
isolated clean browser could start and poll authentication. The affected
browser, however, received exact HTTP `403 {"error":"csrf"}` from
`POST /api/auth/start`.

The browser carried an expired or revoked HttpOnly session cookie. The
security middleware treated the mere presence of that cookie as an
authenticated mutation and required CSRF before resolving whether the cookie
still represented a user. `/api/auth/session` therefore correctly reported an
anonymous state while the public action needed to start a new login remained
blocked. Telegram, the static admin page and the auth handlers themselves were
healthy.

No browser cookie value, database row, client record, contact, order, file or
message was read or copied during diagnosis.

## Bounded intervention

For a cookie-bearing request, the middleware now resolves the session only in
the exact `POST /api/auth/start` branch. If and only if `_session_user()` is
`None`, it invokes the unchanged public handler as an anonymous request and
deletes the stale session and CSRF cookies from the response.

- A valid session still requires exact production Origin, matching
  header/cookie CSRF values and the existing database-bound token check.
- Every other unsafe route remains fail-closed.
- `PUT`, `PATCH`, `DELETE` and near-miss auth paths do not enter recovery.
- Handler rate limiting and response status remain authoritative.
- The guest-access cookie is not cleared.
- `/api/auth/start` does not mint an authenticated session. A new cookie
  session can still be created only by the existing confirmed auth poll.
