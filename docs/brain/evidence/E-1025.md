## Problem and bounded intervention

On the compact configurator, opening a mobile software keyboard hid the only
current-step action together with the full taskbar. A visitor could still type,
but had to close the keyboard and rediscover the primary before continuing.
This affected the exact high-intent practice-support route as well as the
generic configurator and could interrupt a qualified 14,000 RUB intent without
improving scope, trust or price understanding.

The change reuses the existing `#conceptTaskBar` primary as one compact shelf
above the software keyboard. It does not add a second CTA, route, submit path,
price, discount, timer or promise. Activation is page-local and requires all of
the following: mobile width, a focused input/textarea/select inside the current
wizard, software-keyboard occlusion above 140 px, a visible taskbar and no
consent bar.

The browser-specific fixed-position behaviour is measured before applying an
inset. If fixed content already follows the visual viewport, the inset remains
zero; otherwise it equals the obscured layout-viewport area. The active field
is scrolled only enough to stay above the validation reason and shelf. Closing
the keyboard restores the unmodified full taskbar.

The only related layout correction makes the mobile contact review and its
summary shrink within the viewport. It was exposed by the executable 40-character
boundary token; it does not change content, price or desktop geometry.

`30a7f4a3e3d8a64b4319687818c23ecb8749852c` reported GO with

The executable journey starts from the supplied-material practice-support
scope, 39 characters and a 14,000 RUB orientation. It proves:

- one visible primary; 39 characters keep the existing reason and disabled
  primary;
- the focused field is at least 16 px and stays above both reason and shelf;
