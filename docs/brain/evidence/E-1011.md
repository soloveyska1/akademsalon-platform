## Proven application path

- Canonical frontend inventory and tests enforce exactly two tracked order
  producers through one shared helper: configurator and guide microlead.
- The helper owns cryptographic request identity, atomic browser state,
  fingerprint, single-flight and ambiguous retry; the default smoke refuses
  unsafe methods.
- Cookie-auth mutations use exact-origin double-submit CSRF; guest creation
  requires contact, consent and current consent document.
- `/api/orders` checks existing request identity and normally returns the same
  ID for same-owner/same-fingerprint retry. A partial unique index also handles
  parallel insert races.
- Initial persisted status is `new`. Guest response creates an HttpOnly guest
  session and one-time claim exchange. The backend exchange returns exact
  `order_id`; order list/detail and admin detail can read the exact case.

## Reproduced blocking gaps

1. Simple `create_order` commits the order at `app/db.py:1251-1259`; its created
   event commits separately through `add_event` at `app/db.py:1754-1759`.
   Bundle creation is transactional, but the ordinary path can become partial.
2. `app/webapp.py:2678-2709` schedules group/admin/client/mail work through
   process-memory `_bg`. `_bg` retries only in the running process at 0, 45 and
   180 seconds. There is no durable new-order outbox or delivery receipt.
3. No allowlisted marker/test sink or exact request-ID admin lookup exists.
   Purge is exact-ID/payment-aware for DB tables, but source contains no
   Telegram `delete_message`; forum topics/messages can outlive the purged row.
4. The server fingerprint in `app/webapp.py:2243-2274` covers selected fields,
   not the complete semantic request. The unique-index race recovery does not
   repeat the earlier owner check.
5. Frontend confirms 2xx + `ok:true` + safe ID without binding `id == order.id`
   or requiring status `new`. The claim-exchange response contains exact
   `order_id`, but cabinet code ignores it and can open another first active ID.
6. Upload is not content-bound. `configurator.html:786-794` uses a 32-bit FNV
   metadata hash; two different synthetic PDF names with identical other
