## Problem and bounded intervention

The configurator visibly said that contacts and files were not saved, but the
legacy plan-service draft still wrote `name` and `contact` into localStorage.
Separately, a file-dependent request could be restored on the contact step
after a reload had removed its in-memory attachment. The ordinary Next action
was disabled, but cart checkout and a defensive submit path could still bypass
the missing-material prerequisite.

One page-local checkpoint now makes the existing promise true end to end:

- both legacy draft keys remove any old `fields.name` and `fields.contact`
  residue on the next configurator load;
- autosave keeps the working topic, deadline and requirements, but never writes
  or restores the name, contact or consent;
- every transition to contact, including history restore, cart checkout and
  defensive submit, uses the same material prerequisite;
- if an in-memory file disappeared, the request returns only to Materials and
  visibly explains how to continue by reattaching a file or writing at least
  40 characters;
- the selected work, 14,000–19,500 RUB range, deadline, cart and authorship
  choice are retained.

The intervention changes no CSS, price, discount, offer, backend, admin,
analytics event or submission schema. Contact and consent remain memory-only;
no sessionStorage exception was introduced.

## Chromium journeys

Local static origin, exact `practice + draft + support` route, synthetic and
non-sensitive inputs only; no form submission was made.

1. A real file chooser attached one repository text file. The request reached
   Contact with one file and the 14,000–19,500 RUB orientation. Reload removed
   the file and restored Materials with zero files, the same scope/price/deadline
   and the explicit file-loss notice. The sole primary was disabled.
2. A persisted description of 40 characters enabled the existing `К проверке`
   action; Contact survived reload because no missing in-memory prerequisite
   remained.
3. With a synthetic one-line cart precondition, the real cart drawer action
   `Продолжить · контакты` was clicked while evidence was absent. The drawer
   closed, the visible wizard stayed on Materials, the 14,000–19,500 RUB cart
   stayed intact and focus moved to the recovery notice. With a 49-character
   description, the same real cart action reached Contact.
4. The former plan-service leak was repeated through the visible UI: reach
   Contact, enter a synthetic marker, use Browser Back, edit a working
   requirement and wait for autosave. Neither local draft contained the marker;
   safe service answers remained. Independently seeded old residue in both
   legacy keys was removed on reload while topic/deadline/details survived.
5. The first independent UX review found that initial reload moved the state
   to Materials before the first render but did not focus or reveal the notice
   after that render. It also found that the notice stayed stale after a real
   reattachment. The follow-up implementation now performs post-render focus
   and clears the notice as soon as a file or a sufficient description makes
   the prerequisite true. A fresh 360 px reload placed the initial notice at
   318.74..458.30 with focus on the status; a real file chooser then removed
   the notice, showed one file and enabled the same primary.

Only the expected localhost-to-production auth-session CORS messages appeared;
there was no product JavaScript exception. No production contact, order or file
was read or changed.

## Privacy, commercial and inference boundary

The change prevents shared-device contact residue and rejects incomplete
high-intent requests before they become ambiguous leads. It preserves the
visitor's chosen scope and price instead of silently restarting or downgrading
the quote. This protects trust and reduces manual re-qualification, but it does
not prove conversion or revenue uplift. Production publication, production
smoke and rollback remain unverified at this revision.
